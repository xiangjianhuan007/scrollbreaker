# 架构

## 一句话

`截图 → dHash 去重 → OCR → 页面定性 → 四道闸门 → 合并或新起 → 带 scene 的记录`

每一环都可以单独替换，除了中间那个「四道闸门」——那是这个项目的核心。

## 数据流

```
  ┌─────────┐   像素层去重    ┌────────┐   行文本    ┌────────────┐
  │ 截屏源  │ ─────────────→ │  OCR   │ ─────────→ │ 页面定性    │
  └─────────┘  dHash≤6 跳过  └────────┘   clean    │ page_type  │
                                                    │ head_anchor│
                                                    └─────┬──────┘
                                                          │
                                              ┌───────────▼────────────┐
                                              │  四道闸门（Accumulator）│
                                              │  时间 / 类型 / 页头 / 重合│
                                              └───────────┬────────────┘
                                                          │
                                     ┌────────────────────┴────────────────┐
                                     ▼                                     ▼
                              Mode.ROLL（合并）                      Mode.NEW（新起）
                              m.text = 累积全文                      m.text = 本页首屏
                                     └────────────────┬────────────────┘
                                                      ▼
                                 {"scene": "<page>|<anchor>", "text": ...}
```

## 为什么需要「页面类型」

只看重合行是不够的。真实场景里：

```
文章页： 正常 / 好的 / 收到 / 在看 / +关注 / 正文段落…
聊天页： 正常 / 好的 / 收到 / 张三: 机台停一下 / 李四: 马上
重合行： 3 行（正常、好的、收到）
```

按「重合≥2 就拼」的规则，这两屏会被拼成一条。**数据就这样坏了。**

所以第一步是给每屏定性：

| 类型 | 判据 |
|---|---|
| `article` | 命中阅读页特征（+关注 / 写留言 / 阅读原文 / 在看 / 点赞） |
| `chat` | ≥2 行符合「发言人: 内容」形态 |
| `list` | 命中列表特征（[图片] / [语音] / 折叠置顶 / [3条]） |
| `text` | 以上都不命中 |
| `mixed` | **同时**命中文章特征和聊天/列表特征 → 切页中间态 |

`mixed` 是关键：它意味着「这一屏本身就是拼出来的」，所以既不能当累积起点，
也不能被吸收，只能单独成条。

## 为什么页头锚点对文章页要放宽

聊天页的页头是联系人名，滚动时**不变**，所以锚点可以直接用。
文章页的页头是标题，滚动时**会滚出屏幕**，锚点必然变——但文章还是同一篇。

所以：

```python
g3_pass = True if ptype == ARTICLE else (prev_head == phead)
```

这也是「类型」这一层的价值：知道自己在哪类页面上，才知道哪个判据该松、哪个该紧。

## 为什么聊天页的锚点要用「发言人集合」

聊天页有两种形态，实测都存在：

1. 页头（联系人名）在屏幕顶部 → 直接用第一行
2. 页头已经滚出屏幕 → 第一行其实是「张三: 消息内容」，会随滚动变化

形态 2 下用第一行做锚点，同一会话也会被误判成换页。所以退化到
**本屏出现过的发言人集合**（排序拼接）——同一会话的发言人集合稳定，
不同会话几乎不重合。

## 为什么重合判定要用「上一帧原始观测行」

文章页要剥掉顶部的通知横幅（否则「张三: 在吗」会混进正文）。
但如果把剥离后的结果存为「上一帧」，下一帧就再也算不出重合了 ——
因为被剥掉的那几行恰恰可能是重合的。

所以内部状态分两份：

```python
self._prev = {
    "lines": merged,   # 剥过横幅的、用于输出和继续合并
    "raw":   keep,     # 本帧原始观测行，专门用于下一帧的重合判定
    ...
}
```

这是实现里最容易踩的一个坑，`test_article_scroll_ignores_anchor` 就是它的守卫。

## 可替换点

| 环节 | 替换方式 |
|---|---|
| 截屏 | 自己传 `Frame(lines=..., ts=...)`，不用内置的 `watch` |
| OCR | 实现 `read(bytes) -> str`；或直接用 `CallableOCR` 包自己的函数 |
| 判定阈值 | `Config` 里全部可调：时间窗、行数上限、重合数、各类正则 |
| 输出 | `Merge` 是纯 dataclass，自己落库/做向量化/喂模型 |

## 明确不做的

- 不读任何应用的数据文件、数据库、内存
- 不注入进程、不需要管理员权限、不联网
- 不做「绕过鉴权」类功能
